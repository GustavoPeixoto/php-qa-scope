## Why

The package needs a PR-based release process that keeps its Composer metadata consistent with its Git tags and rejects invalid version progression before publication. Release preparation must also produce a meaningful PR when all product changes are already on `main`; updating `composer.json` provides that change without introducing a separate version file.

Release validation currently defines PHP and Composer separately from the local PHP image. A shared stage in the existing Dockerfile will keep development and CI on the same declared runtime versions without building development-only Xdebug tooling for release checks.

The original publisher embedded a substantial Python `authority` step in YAML and duplicated release rules and GitHub tag queries. Group 8 extracted modular scripts and completed their local verification, bringing the completed task count to 39. The follow-up in group 9 standardizes checkout step names and removes the publisher's optional checkout destination, making the common checkout behavior easier to recognize without changing automation provenance or publication checks.

## What Changes

- Introduce release PRs from same-repository branches named `release/vX.Y.Z` to `main`. The branch declares the intended version; the PR must set `composer.json`'s `version` to the identical `X.Y.Z` string.
- Accept only stable versions with canonical non-negative integer components. Reject prerelease/build suffixes and leading zeros. With no published stable tags, require `0.1.0`; otherwise allow exactly the next patch, minor, or major relative to the greatest published stable version.
- Keep the required `Validate Release Branch` check and the workflow's existing PR events to `main`, but put a single `release/` prefix condition on the validation job. Ordinary PRs, including forks, skip the entire job without allocating a runner; the skipped check does not block merge when other branch rules are satisfied. Remove the ordinary-PR echo step and repeated release conditions on individual steps. All release-prefixed PRs enter validation, including malformed names and forks, so unsupported releases fail explicitly. Release PRs also undergo strict Composer validation, with only Composer's advisory about declaring `version` explicitly disabled.
- Extract a shared `tooling` stage in `docker/php/Dockerfile`, inheriting the existing PHP base and providing Composer once. Make `development` inherit it, retaining development-only Xdebug, user/workspace setup and configuration. Replace `shivammathur/setup-php` in both `Validate Release Branch` and `Validate Merged Release` with builds of the `tooling` target from each job's exact checked-out commit and run strict Composer validation in that image. Python and `gh` remain on the runner; the publisher retains its existing credential isolation. Preserve the currently declared PHP/Composer versions rather than introducing a version upgrade.
- After an eligible PR merges, revalidate the merged manifest and current remote tags, then create a lightweight `vX.Y.Z` tag at the PR's integrated commit using the `release-bot` GitHub App. Serialize publication, fail safely on stale versions or existing tags, and never move/delete tags.
- Extract the inline `authority` step into `tools/release/authority.py`. Share pure release rules through `contract.py` and read-only GitHub API/tag-enumeration logic through `github_api.py`, retaining `validate.py` as the checkout-validation entry point. Load the publisher's automation from the exact revision containing the executing workflow, separately from the package commit being released. Recheck current remote state within the existing serialized publisher before obtaining App credentials, and preserve the `authority` step's `tag` and `sha` outputs.
- Name all three checkout steps across `validate-release.yml` and `create-release-tag.yml` exactly `Checkout repository`. Omit the publisher's optional checkout `path`, use the default job workspace, and invoke `python3 -I -B tools/release/authority.py`. Use a standard full checkout for the publisher and retain each job's existing commit selection: PR head, integrated commit, or executing workflow revision.
- Require PRs and successful automatic checks on `main`, with zero required human approvals in this initial phase. Independent reviewers, mandatory CODEOWNER review, stale-approval dismissal, and approval of the latest push are not activation prerequisites. Preserve tag protection and the main deletion/force-push restrictions without adding main bypasses.
- Complete this change with the release infrastructure implemented, activated and validated, including its operational guidance and evidence. Executing a real release is outside this change's scope and is not a completion prerequisite. Document bootstrap, failure recovery, and the distinction between verified infrastructure and unexercised live publication.

Out of scope: executing a production release or its live acceptance; a `VERSION` file; automatic version selection; prereleases or build metadata; maintenance release lines; GitHub merge queue integration; GitHub Release creation; changelog generation; deployment; automatic Packagist registration or webhook configuration; and changes to package CLI behavior or local pre-push policy. The authority refactor does not replace GitHub API operations with Git commands, remove either post-merge job's existing event condition, change version rules, or alter protection policies.
